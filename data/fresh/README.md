# Fresh evaluation set (plan §6.9)

About 150 requirements from public documents published **from 2025 onwards**, used only for
evaluation (never for training or prompt iteration). It answers two questions: do results hold
outside PROMISE, and were PROMISE results inflated by models having seen it?

## Collection rules

1. **Sources:** public requirement documents (SRS, specifications, technical requirements in
   tenders or open-source projects) dated 2025 or later, under a license that allows reuse
   (MIT, Apache-2.0, CC BY, CC0, or an explicit public-sector reuse license). Search ideas:
   GitHub repositories created since 2025 with `SRS`, `requirements specification` or
   `software requirements` in the README or file names (filter by license); public tender
   technical specifications in English.
2. **Spread:** at least 5 documents, **at most 40 requirements per document**.
3. **Extraction:** copy sentences that are requirements (usually contain shall/must/will or a
   numbered requirement format) **verbatim**, fixing whitespace only. Do not write or rephrase
   requirements yourself: knowing the taxonomy would bias the wording.
4. **Provenance:** one row per document in `documents.csv` (URL, publication date, license,
   retrieval date, version or commit). If a license does not allow copying text, keep only
   `location` (section/line) in `requirements.csv` and leave `text` empty; it will be fetched
   at evaluation time.

## Automated collection (`uv run reqbench fresh collect`)

Decided on 2026-10-10: collection is automated and **rule-based only** (no Claude, no Jev,
which would bias the set towards the systems under evaluation). Humans only annotate.
Code: `bench/src/reqbench/fresh/`.

1. **Search** (`gh api`, authenticated), union of two sources:
   - repository search (`QUERIES` in `github.py`): created since 2025-01-01, license MIT,
     Apache-2.0, CC-BY-4.0 or CC0-1.0, not forks or archived;
   - code search (`CODE_QUERIES`): files such as `SRS.md`, `requirements.md`, `SRS.txt` or
     `docs/*.md` with *shall* and "functional requirements". It finds SRS files in repositories
     named after the product, which the repository search misses (on 2026-10-10 it mostly
     returned tools *about* SRS). Date, license and fork status are then checked on the
     repository metadata, before listing any files.

   The first run freezes results, HEAD commit and file list in `data/raw/fresh/snapshot.json`
   (git-ignored, saved every 100 repositories, resumable); blobs are cached by git SHA.
   `--refresh` re-runs the search. When the API rate limit is hit, calls wait and retry.
2. **Repository filters:** generators, templates, prompt/LLM tools, agents, plugins and
   "awesome" lists are excluded by name/description (`EXCLUDE_REPO`), and repositories named
   example/sample/demo/tutorial. Document files: `.md`/`.markdown`/`.txt` whose path mentions
   SRS, requirement(s) or spec(ification); the root `README.md` only when there is no other.
   Skipped paths: third-party copies, blogs, fixtures, examples, tests, `*template*` folders,
   prompts, agent skills and instructions (`SKILL.md`, `AGENTS.md`, `CLAUDE.md`, `.agents/`,
   `.claude/`, `.kiro/`…).
3. **Extraction rules** (`extract.py`): skip code blocks, HTML comments and headings; split
   paragraphs, list items and table cells into sentences; remove markup and leading IDs or
   short labels (`FR-01:`, `Description:`); keep sentences with *shall* or *must*, 6–60
   words, starting with a capital letter or digit (not with the modal itself), in English,
   without placeholders (`[ ]`, `{ }`, TBD/TODO), questions, a trailing colon or RFC 2119
   boilerplate.
4. **Contamination filter:** sentences with similarity ≥ 0.85 to any PROMISE or Dalpiaz
   (dronology, leeds, reqview, wasp, promise-reclass) text are dropped; a repository with
   ≥ 3 such sentences is dropped whole (probably a copied template). Also dropped whole:
   documents that declare AI generation ("generated by ChatGPT/Claude/an LLM…") and
   Kiro-style generated specs (≥ 50 % of sentences like `THE X SHALL …`).
5. **Draw** (seed 20261010): a repository counts as a document if it keeps ≥ 10 candidates.
   Documents are visited in a stable hash order; at most one per owner; every file used must
   have been first committed in 2025 or later; up to `--per-doc` (default 15, cap 40) random
   sentences each; near-duplicates (≥ 0.90) of sentences from another document are skipped,
   and a document sharing ≥ 50 % of its sentences with a chosen one is skipped as a mirror;
   stop at `--target` (default 170, margin for non-requirements). Rows are shuffled.
6. Dry run by default; `--write` writes both CSVs and `data/manifests/fresh_v1.json`, and
   refuses to overwrite a `requirements.csv` that already has annotations.

**Known limitation:** many 2025–2026 public SRS files are probably written with LLM help
without saying so. No deterministic rule can detect that; it is a validity threat to report
with the fresh-set results.

`location` is `path#Lnn` (first line of the paragraph, list item or table row) at the
pinned commit. `published_date` is the oldest commit date of the files used.

## Annotation

- Design (deviation of 2026-11-10, `docs/PREREGISTRATION.md`): annotator **A** labels all
  sentences; annotators **B** and **C** each label a disjoint subsample of 30
  (`second_annotator` = `b`/`c`), drawn by `uv run reqbench fresh assign` (seed 20261010,
  stratified by A's label, only after A has finished). Everyone labels **independently**,
  without seeing other labels or any model output, using the leaf definitions in
  `questions/taxonomy_v1.yaml`: functional, performance, security, usability,
  operational_constraint, other. `discard` marks a sentence that is not a requirement (the
  extraction rules over-collect on purpose); a row is dropped when its final label is `discard`.
- A: `uv run reqbench fresh annotate` opens a local page (127.0.0.1:8765) with the definitions,
  keys 1–7, and saves each choice straight into the annotator's column; it never shows another
  annotator's column (B and C, if they use it, only see their subsample).
- B and C (phone, by link): `uv run reqbench fresh form --who b` renders a one-page checklist
  (template `bench/src/reqbench/fresh/form.html`) with their 30 sentences and the same
  definitions, never anyone's labels. It is published as a claude.ai artifact (shared by link);
  progress stays in their browser, and "Enviar por WhatsApp" opens a prefilled message
  (`Respuestas del anotador B: 1F 2S …`) for `fresh reply`. Published on 2026-11-10:
  B https://claude.ai/artifact/RUv3yboLfsRPEWCg5mHHr3 · C https://claude.ai/artifact/7vu4HFL5269idTwqrUnXFQ ·
  reserve D https://claude.ai/artifact/5GuqNp18tA3pHi4EDasMuH (`fresh assign --who d`: a
  further disjoint 30 from the rows without a second annotator).
- B and C (plain text alternative): `uv run reqbench fresh message --who b --copy` copies a plain-text
  checklist (letter legend with the same definitions + their 30 sentences, never A's labels).
  They answer `1F 2S 3O …`; copy the reply and run `uv run reqbench fresh reply --who b --paste`
  (or `--file reply.txt`). It checks that every item is answered exactly once with a valid
  letter, and never overwrites existing labels.
- `uv run reqbench fresh kappa`: Cohen's κ for A–B, A–C and pooled, on leaves (with `discard`)
  and on level 1 (rows where neither says `discard`), with bootstrap 95 % CI and the list of
  disagreements. Computed before adjudication.
- `adjudicated`: the agreed label for the 60 double-annotated rows (disagreements discussed,
  reason in `adjudication_note`), A's label for the rest.
- Freeze the file (commit) **before** any system is evaluated on it.

## Files

- `documents.csv`: `doc_id,title,url,published_date,license,retrieved_at,version_or_commit,max_requirements_taken,notes`
- `requirements.csv`: `req_id,doc_id,location,text,annotator_a,annotator_b,annotator_c,second_annotator,adjudicated,adjudication_note`
  (`req_id` format: `fresh-0001`).
